## Shape
One Python process, run as a user systemd unit and bound to IPv4 loopback on `127.0.0.1:8741`. There is one deploy, from the one branch `main` (see Deploy). The process does three things:
- Polls herdr, the session registries and the transcript stores, and writes its SQLite database under `~/teams/atlas/data/` (`atlas-dev.db`).
- Serves the page and a small JSON API from that database.
- Keeps the health of each source for the footer.

`tailscale serve` puts HTTPS on the node's tailnet name in front of it: port 443 to `127.0.0.1:8741`. The Atlas processes listen on loopback only; the tailnet listener is Tailscale's. The index goes to no third party. Its one way off the box is the page, served to devices on the tailnet, as the spec allows.

**Whose headers count.** `Tailscale-User-Login`, `Tailscale-User-Name` and `X-Forwarded-For` count only when the client end of the connection belongs to uid 0, which is tailscaled, running as root. Atlas finds that owner in `/proc/net/tcp`, on the row whose local address is the request's peer and whose remote address is Atlas's end, in state ESTABLISHED only. The kernel shows uid 0 for a socket its owner has already closed, so a process that sent the headers and closed at once would otherwise pass as tailscaled. The reason: any process on this box can call `127.0.0.1:8741` with Dylan's headers. Without this check, a sandboxed agent that reaches localhost but not the herdr socket would get `typist`, the send token and keystrokes into every pane.
- **When the owner is not uid 0,** or cannot be found, the request is anonymous. It is not a typist, gets no token and no stored last look, and `/api/send` refuses it as `not-serve`.
- **The check lives in `identity()`,** the one helper that reads those headers, so `whoami` and `viewer` share it.
- **`ATLAS_SERVE_UID`** may name another uid on a check instance only. The deploy unit refuses to start when it is set.

**Devices.** `ATLAS_TYPIST_DEVICES` lists stable node IDs (`Node.StableID` from `tailscale whois`), not names. A rename in the admin console cannot lock Dylan out or let a renamed node in. `/api/whoami` still shows the name as `device`.

Python 3.14 standard library only: `http.server` (threading), `sqlite3`, `tomllib`, `json`, `shlex`, `subprocess`. The front end is plain HTML, CSS and JavaScript, served as static files with vendored fonts. There is no build step. The Teams page at `/office` is an org chart (spec 2026-10-31-org-chart): cards in nested lists, with its square lines drawn as CSS borders.

## Restart and wipe
- A restart keeps the database. Every name, placement and `state_since` in it survives. On start the process replays the transcript files modified in the last 25 hours to rebuild its in-memory match evidence and offsets, and upserts message rows by their stable keys, so a replay never adds a second row. `session_names` (below) keeps the observations a replay needs, so pairs made before the restart are made the same way after it.
- A wipe is `python3 -m atlas --reindex` with `ATLAS_DB` set and the service stopped. It drops and creates again only the index tables (`agents`, `screens`, `session_names`, `messages`, `source_health`, `team_status`, `reports`), in one transaction. The next start rebuilds them from the sources. Deleting the file is no longer the wipe, because it would also lose the kept tables below. Only a wipe can lose what the sources do not hold; see "What a wipe cannot give back".
- Four tables are kept through a wipe, because no source can rebuild them. `observations` holds what Atlas saw change in each team's STATUS and decisions files: a STATUS file keeps only its current lines, so the history of a line exists only here. `first_reads` records which of those files Atlas has read, so a re-read after a wipe is never mistaken for a first read. `last_look` holds each Tailscale login's last look at the briefing, which exists only as a viewer's action. `sends` is the typing audit (schema 7).

## Sources and pollers
Three independent threads, so a slow transcript scan never delays state or screens. Each subprocess call has a timeout (5 s).

| Source | How read | Interval | Measured cost (report, 3:04 to 3:06 PM ET) |
|---|---|---|---|
| herdr state | `herdr api snapshot` (one call, all agents and panes) | 2 s | 3 ms |
| Pane screens | `herdr agent read <pane> --source visible`, each live pane | 4 s | 92 ms for 25 panes |
| Session registries | the glob `*.json` exactly in `~/.claude-org/sessions`, `~/.claude/sessions`, `/data/home/.claude/sessions`. The `.key` files beside them hold secrets and are never opened | 5 s | a few dozen small files |
| Claude transcripts | the three `projects` stores; each `.jsonl` modified in the last 25 hours, then only bytes past the in-memory offset, complete lines only | 5 s | stat of about 940 files, plus new lines |
| Codex transcripts | every `~/.codex/sessions/**/*.jsonl` modified in the last 25 hours, same tailing. A long-lived rollout stays in its start date's folder (`code-audit` started on 2026-10-06), so the window is by modification time, not by folder | 5 s | stat of about 1,430 files, plus new lines |
| Structure | `structure.toml` in this repo | at start and when its mtime changes | none |
| STATUS and decisions | each team's `status` and `decisions` path in `structure.toml`, read only, again only when the file's mtime changes | 5 s | a stat per file |
| Reports | each team's `reports` folder in `structure.toml`: every `*.md` statted by descriptors (no symlink followed, hidden entries and `*.key` never opened); read only when changed since Sat 10-31 1:32 PM ET or linked from STATUS, under 1 MB, and again only when its mtime or size changes | 30 s | 22 ms for about 5,500 files, none read (first pass 27 ms, 56 read) |

A file whose inode changes or whose size shrinks is read again from the start. The same Claude session copied into two stores, or under two project folders, is one session: events are keyed by session id and event `uuid`, never by path.

## Source health and failure
Table `source_health`: source, `state` (`ok`, `degraded`, `failing`), `last_ok_at`, `failing_since`, `last_error`, `files_failing` (count, for the transcript stores).
- herdr: a non-zero exit, a timeout or JSON that does not parse is a failure. On failure nothing in `agents` or `screens` changes; the page shows the last rows with `last_ok_at`. Gone is derived only from a successful snapshot. A successful snapshot with zero agents is a valid empty source, not a failure.
- A transcript store whose root cannot be listed is `failing`; one that lists but has files that cannot be read is `degraded` with the count.
- The `messages` table changes only after a transcript poll in which every store was `ok`, and after a restart or wipe only once the replay of every store has finished. While any store is `failing` or `degraded`, `messages` is frozen at its last good state and the footer marks it with that time. A partial read can therefore never delete, rewrite or re-pair a row.
- `failing_since` is set on the first failure after an ok and cleared on the next ok. The footer shows it in ET with UTC in brackets.

## Data
- `agents`: herdr name (the node key), pane, tab, workspace, runtime, status, session id, `state_since`, `state_since_exact`, cwd, terminal title, last seen, placement rule. `state_since` resets when the status changes, or when the pane or session behind the name changes. `state_since_exact` is false for a status already set at the first poll after a wipe (a restart keeps the stored value when the status is unchanged), and hover says "since at least" until the next change.
- `screens`: pane, herdr name, text, read at. Latest only.
- `messages`: key, time, kind (`send`, `receive_only`, `prompt`), from session, to session, from and to herdr names when known, from and to raw names, first line (140 characters), delivered or failed, ambiguous flag.
- `session_names`: every observation the sources forget: registry name, messaging socket and session id from the registry files; herdr name, pane and session id from each snapshot; first and last seen. Never pruned by the 25-hour window while a session it names still has rows.
- `source_health`, as above. A decisions file's row also counts the entries skipped because their leading stamp did not read cleanly.
- `agents` also carries each Claude agent's now line: its own words for its latest step, read while tailing its transcript (a Bash call's description; Reading, Editing or Writing and a file's base name; or Helper: and an Agent or Task description), with its time. Never the command, any other input, or any output. Null for Codex. It changes within one transcript poll of the step and is cleared when the session behind the name changes.
- `team_status`: each team's first Working on, Last shipped and Waiting on Dylan (or Waiting on you) line in the first 20 lines of its STATUS, as written, with the file's modified time.
- `reports`: one row per report read, keyed by its absolute path. A report is read when its mtime is at or after Sat 10-31 1:32 PM ET (Dylan's For Dylan rule) or when the team's STATUS links it: a whole Markdown link's `*.md` target, then a `*.md` path in backticks, then, in what is left once those and every URL (`scheme://` to the next space) are masked, a bare path that starts with `/`, `~/` or `./` or holds a `/` (trailing `.,;:)` dropped); a path starting with `~` counts only as `~/`, never another account's home, on the Waiting on Dylan line or in a `## For Dylan` section, tried from the STATUS file's folder and then from each of the team's roots, and counted only as a regular file inside the team's `reports` or `folders`. Fields: team, name (relative to the reports folder, without `.md`), title (first `# ` heading, else the file name), written time and how it was found (`header`: a clock time in the preamble, the first 15 lines before the first `## ` heading and outside code fences, on a line containing "written", else on the `From ` line, with its date and, when given, a matching UTC bracket; a block's text or a fenced sample never counts; `frontmatter` or `filename`: the date alone; else `none`), author (the first `From ` line in the first 15, else frontmatter `author`), the change block (`## For Dylan`) and the ask block (`## For Dylan: ask`) each as JSON keyed by label exactly as `records/specs/for-dylan-blocks.md` spells them, `asked_at`, the first pull request link, and whether STATUS links it now, with that line. Nothing looser counts: a heading that is not exact, a heading in a code fence, or a label spelled differently is not read. An older report read while STATUS linked it keeps its row once unlinked (linked false, no STATUS line) while its file is unchanged, so its ask page can say it is no longer asked; it is never in `/api/changes`. A re-index loses such rows, since nothing links them: accepted. Only a complete pass deletes rows; a missing folder is `failing` and keeps them. `/api/changes` and the briefing's `changes_since` leave out, by one shared condition: a report whose only block is an ask (spec criterion 3, amended 5:35 PM ET); a brief (its title's first word is Brief); and a report whose own written time, or written date when only a date is known, is before the rule's start (F2 of the acceptance, 6:15 PM ET). One with no block stays; one with no written date keeps the mtime rule. Served by `/api/changes`, `/api/change`, `/api/ask`, `/api/report-file` (images only, through descriptors from a team root) and the briefing's `asks` (linked reports with an ask block only) and `changes_since`.
- `observations` (kept): team, kind, value, `first_seen`, `written_at`. A row when a three-line value differs from that team's latest row of that kind, including a line that is cleared (value null) or comes back. A row the first time a decision appears. A decision is its team, its written time and its order among that file's entries with the same written time (`seq`), not its text: an edit to its words updates the row's value, keeps its `first_seen`, and is never new (schema 5; the migration merged the edits recorded earlier as new rows). STATUS log entries are no longer recorded: they are agents' working notes, and rows recorded before stay but are never shown. A decisions entry counts only when its leading stamp gives a date and an ET clock time cleanly: hour 1 to 12, minutes 00 to 59, any bracket after the time exactly `(H:MM UTC)` or `(HH:MM UTC)` and equal to the ET time converted, and an instant that reads back in America/New_York as exactly the written date, hour and minute. A time the spring change skips never counts; one the autumn change repeats counts only when its UTC bracket settles which of the two it is. Any other entry is skipped and counted.
- `first_reads` (kept): team, kind (`status` or `decisions`), path as `structure.toml` spells it, time. What a file holds at its first read is the baseline, even when nothing in it parsed, and a new path gets its own: `first_seen` is the entry's own written time when it parses, else null, and null is never new. Starting to read a file therefore never floods the feed.
- `sends` (kept, schema 7): one row per `POST /api/send`. Each row holds the time, the login and device as resolved (with the device's stable ID), the agent and its pane once checked live, the kind, the key for a key, the length in characters for a line, and the outcome: `sent`, `failed`, `refused:<reason>`, or `sending` while herdr runs. A send from a box carries `client_key` (schema 17), a random word the page made for that press and keeps for retries of the same words: a unique index lets one request take it, and any other gets 409 `already-sent` (audited `refused:repeat`, no key). `GET /api/send-status?key=` gives a key's outcome and time to the typist, for a page that lost the reply. It never holds the text.
  - **The checks, in order:** the connection comes from tailscaled (`not-serve`), the typist (`not-typist`), `Sec-Fetch-Site` exactly `same-origin`, with a missing header refused (`cross-site`), and the per-process send token from `/api/whoami` in `X-Atlas-Send-Token`, compared with `hmac.compare_digest` (`token`).
  - **Then the body:** exactly one `Content-Length` of 1 to 4 ASCII digits, no `Transfer-Encoding` header at all (`framing`), and at most 8 KB of JSON. The agent must be a named, live herdr agent in the current read, or the reason is `gone`. A line is 1 to 4,000 characters with none in Unicode categories Cc, Cf, Zl, Zp or Cs: controls, bidi and zero-width format characters, line and paragraph separators, and unpaired surrogates. The agent name is held to the same rule. A key is one of Enter, Esc, Tab, Shift+Tab, Ctrl+C, Up, Down, Left, Right, Backspace, y or n. A char (`kind` `char`, the character in `key`) is one printable ASCII character, 0x20 to 0x7E, sent with `send-keys` as itself, or as herdr's `space` and `plus` for those two. Its row records kind `char`, no key and length 1, never the character. A line to a blocked agent is refused (`blocked`); a key is allowed, because keys answer its question.
  - **The send:** `herdr agent prompt <agent> <text>` or `herdr agent send-keys <agent> <key>`, argv only, through `herdr.run`, never with `--wait`.
  - **The answers:** 204; 403 or 400 with `{"reason": ...}`; or 502 with no detail.
  - **Reading:** no endpoint reads the table yet.
  - **Pages:** each team's `artifacts` folder is served from Atlas's own origin at `/a/<team>/<path>` (and `/mocks/` redirects to `/a/atlas/`), so a page's script could otherwise read the send token and post as Dylan when he opens it. Every `/a/` response therefore carries `Content-Security-Policy: sandbox allow-scripts` and a policy that allows loads only from `//<request host>/a/<team>/`, with `connect-src` and `form-action` none. A page runs in an opaque origin: it cannot read Atlas's answers, its requests are not same-origin, and it loads nothing from another host or another team. `/api/whoami` also gives the token only on a same-origin request.
- `last_look` (kept): login, time. `POST /api/seen` sets it, only with a `Tailscale-User-Login` header and only when `Sec-Fetch-Site` is absent or `same-origin`. A request with no login uses the browser's own last look, passed as `?since=`. With no last look, the briefing counts the last 24 hours.
- The briefing's `new` holds only changes to the three lines and decisions, as news. A decision shows Dylan's words, the first quote in it (a question put to him is skipped), as `You: "<quote>"`, after the first sentence of its `Effect:` when it has one. A decision with no quote, or whose result has unbalanced quotes or `**`, is not listed. Where that reading would mislead (a first quote not introduced by a colon, a bold heading or "chose"; a quote cut into parts; an entry that says it is not a decision) the entry is shown without its stamp, as written. Shown text only: the stored entry never changes.

Only first lines are stored. Full texts and their digests used for matching stay in memory. Rows older than 25 hours are deleted on each poll, except agent rows, which leave when a worker has been Gone for 24 hours.

## Messages: how a row is made
Message keys are stable across rebuilds: `send:<session>:<tool_use_id>`, `recv:<session>:<uuid>:<block index>`, `prompt:<receiver session>:<uuid>`. Codex events use `<rollout id>:<ordinal>`, plus the occurrence index of the prompt within the command.

Matching is recomputed, not accumulated. Each transcript poll reruns both matchers over all in-memory evidence for the 25-hour window (in the source checks' window: 342 sends, 285 blocks, about 550 prompt commands) and writes `messages` as a diff in one transaction. It upserts every key the run produces and deletes every key in the window it no longer produces. When a later poll finds the send for a block that was `receive_only`, the `recv:` row goes and the `send:` row carries the pair in the same transaction. When new evidence makes an earlier unique pair ambiguous, that pair is withdrawn the same way. The rows are a function of the evidence alone, so poll and file order cannot change them.

**SendMessage.** One row per send. Its tool result says whether it succeeded and names the recipient's registered name (measured: `"... → engineering-lead-e0 (another Claude session on this machine ..."`). A received `<cross-session-message>` block is evidence for a send, not a row of its own. A send and a block pair only when all of these hold:
- the full texts, whitespace normalized, are equal;
- the block's time is 0 to 120 s after the send's;
- the sessions differ;
- the recipient name's stem (the part before the last `-xx`) equals the basename of the receiving session's cwd;
- where the recipient's registered name is known for that time (a `session_names` row, or a name taught by an earlier unique pair), it is the receiving session; the same holds for the block's `from-name` and the sending session.

Pairs are assigned one to one in time order. If a block still has more than one candidate send, or a send more than one block, none of them pair. Each such send keeps its row, with its raw recipient name, no receiving session and the ambiguous flag, and it draws no edge. A block with no candidate send at all (its sender's transcript is not on this box) becomes a `receive_only` row from its `from-name`. The review's case: two sends of identical text, 5 s apart, to `engineering-lead-e0` and `engineering-lead-e2`. Both receiving cwds end in `engineering-lead`, so the stem rule does not separate them. The registry observation `engineering-lead-e0` → session `aa906e7e` does, and without it both stay unpaired.

An end that no pairing names is resolved through the registry (message names brief, 7:28 PM ET Sat 10-31):
- **An unpaired send** names its recipient by registered name or socket. Its row takes the one session that name or socket belonged to at the send's time, from the registry rows alone (`name_since`, or first seen, to last seen), and that session's herdr name. An earlier unique pair is used for pairing only: it has no end, so it never names an end by itself.
- **A `receive_only` block** is resolved the same way from its `from-name` and its sender's socket, which must agree.
- **No guessing.** When more than one session remains, or the two keys disagree, the end stays unnamed with the ambiguous flag. Delivery is still decided by pairing alone: a send resolved this way keeps `delivered` from its tool result.
- **Why so many sends go unpaired:** the stem rule needs the receiving cwd's last folder to be the recipient's name without its suffix. A lead working in its repo subfolder (`engineering-lead/atlas`) fails it, though the registry knows the recipient exactly.

**herdr prompts.** One row per received prompt: a user entry with plain text that is not runtime-written. Runtime-written text is excluded from the list and the count: `isMeta` entries (skill bodies), `isCompactSummary`, resume text, image notes, tool results, and pasted blocks. The sender is found from command occurrences:
- Extraction: from Claude `Bash` inputs (`command`), and from Codex `custom_tool_call` `exec` inputs. For Codex, the shell command is the JavaScript string literal after `exec_command({cmd:` exactly, decoded as a JSON string; any other spelling, a template string or a concatenation gives no candidate. Nothing is ever executed.
- Occurrences: a small quote-aware scan walks the raw shell text, tracking single quotes, double quotes and backslash escapes, and cuts it into simple commands only at `;`, `&`, `|` and newlines that are outside quotes, except an `&` right after `>` or `<` (the redirection in `2>&1`, which most herdr commands in the transcripts carry). `shlex.split` then splits each simple command into words. Because separators are found in the raw text, a quoted `;` or newline is never a boundary. An occurrence is a simple command whose first three words are `herdr agent prompt`, optionally after an absolute or `~/.local/bin` path to `herdr`. Text that is not in command position (an `echo` argument, a comment, a heredoc body, `bash -c`, `eval`, a function) is not an occurrence; a command holding a heredoc, `bash -c` or `eval` is skipped whole. Options (`--wait`, `--until X`, `--timeout N`) are skipped. One command can hold several occurrences (63 did in the review's window).
- Text: tokenizing drops quote context, so the raw source of the occurrence is checked instead. If it contains no `$` and no backtick, the argument is fully literal and must equal the received text in full, whitespace normalized. Otherwise the literal part is the decoded argument up to the first `$` or backtick, even inside single quotes. That is conservative: it can only shorten a true prefix. It must be at least 20 characters, and the received text must start with it.
- A candidate needs that text match; the receive 0 to 15 minutes after the command; different sessions; and a target that resolves to the receiving session. A target is a herdr name or a pane id, resolved through `session_names` for that time, then the declared agent named by the declared-folder rule of the session-to-name paragraph below, judged against that receive's own cwd (its name equal to the target, and herdr never having seen the session as another agent; a declaration, so it holds for all time and survives a wipe), then a launch command or a `workers/<name>/` folder for the receiving session. A target that does not resolve gives no candidate. Uniqueness of the text alone never names a sender.
- One to one in time order. A receive with more than one remaining candidate, or none, shows "sender not known" and draws no edge.

**Session to herdr name.** In order: herdr's `agent_session.value` (Claude, and Codex when herdr supplies it: `atlas-review-pr1` has one, `code-audit` does not); then a `session_names` row for that session; then a declared folder: a session launched in the `folder` of exactly one agent in `structure.toml` (the cwd of its first event, exactly) takes that agent's name while its latest cwd is that folder or inside it by whole path components and no other declared folder is a longer match (`code-audit`'s rollout runs in `~/herdr/code-audit-agent`); then a launch command, searched only in the files the service reads (modified in the last 25 hours, plus the placement replay below). A `herdr agent start <name> --kind <k> --pane <p>` names the session whose first event is 0 to 60 s after the command, whose cwd equals the pane's cwd at the time, and which is the only such session. Then a worker folder: a session whose cwd is under `<team folder>/workers/<name>/` (the playbooks put every worker there) takes `<name>`. Otherwise the node and its message rows are labelled by runtime and short session id, with hover "herdr name lost in a rebuild", under its team when its cwd matches one team folder in `structure.toml` (longest whole-path-component match). A shared folder such as `~/repos` is never turned into a specific agent.

**Placement rule 1 for unlisted agents.** For each live unlisted agent, and each one Gone for less than 24 hours, its own transcript is read from its first event to find the first message that reached it. The sender is then sought in files modified since that time. This is bounded by the worker's age, not by the 25-hour window. The result is stored on the agent's row, so it survives a restart, and is rebuilt from the sources after a wipe. The sender becomes the agent's parent only when the agent runs in the sender's own workspace (the sender's row, else its declared team's `workspace`). A message from another workspace never places an agent, which then falls to the folder and workspace rules (org chart spec, criterion 6, amended 7:16 PM ET Sat).

**Placement by brief, then parent unknown** (org chart acceptance F1, Sat 8:41 PM ET). When no message names a sender, a worker is placed by the brief that started it:
- **Which brief:** its session's first prompt (Claude or Codex) names a brief inside its team's folders or its `reports` path (Forge keeps its briefs there), either a `*.md` under `<folder>/records/briefs/` or a `*-brief.md` anywhere below.
- **How it is read:** through `open_below` from that folder (no symlink, no `..`), first 64 KB only.
- **The parent:** the first name in backticks on the brief's first line starting `From `, as `placement_rule` `brief`. This holds only for the same session, and only when that agent is on the graph and in the worker's team.
- **Checked against everyone:** after every agent is placed, `settle()` takes the `brief` placements in name order. It demotes any whose parent is not in the same team as finally placed, or whose parents lead back to it (a cycle), to `parent-unknown`.
- **A message first:** a message that reached the session counts only when the message rule can use it (a sender in the agent's own workspace); otherwise the brief is tried.
- **The cache:** the stored placement decisions were cleared once by migration 8, so every live session is placed under these rules, as a wipe would place it.
- **Otherwise:** the folder or workspace rule gives the team alone, as `parent-unknown`, never the team's head as a parent. The Teams page shows such a worker in its team's column under a quiet "Parent not known" line, indented one step inside the team when the chart is stacked.

## What a wipe cannot give back
Only after a wipe, never after a restart. The kept tables are not affected:
- `state_since`: marked "since at least" until the next change.
- A Gone worker's herdr name, when neither a declared folder, a launch command nor a `workers/<name>/` folder names its session: the node and its message rows show runtime and short session id, hover "herdr name lost in a rebuild". Accepted as criterion 22's second exception by the product lead and the Atlas lead, 3:21 PM ET; no observation log, no second store.
- Which workers are Gone, and since when. herdr forgets closed panes and the registry forgets ended processes, so after a wipe the only record of an ended worker is its transcript. The rebuilt Gone set is the unlisted sessions with a transcript event in the last 24 hours that are not live. Their Gone time is their last transcript event, which is never later than the real one. Two effects: a rebuilt Gone worker can leave the graph earlier than it would have, and a worker silent for 24 hours before its pane closed does not come back at all. Accepted into the same wipe-only exception by the Atlas lead and the product lead, 3:28 PM ET (spec draft 2.2). Hover on a rebuilt Gone worker says "last active <time>", not "Gone since".

A restart has no exceptions. Gone time is `last seen` in `agents`, the last successful snapshot that held the agent, and it is in the database. Its precision is the gap between successful herdr snapshots: 2 s while polling is healthy, widened by any time the service was stopped or herdr reads were failing (the footer's source health shows the latter). A pane that closes during such a gap is last seen before it. On a deploy restart the gap is a few seconds.

## Answers to the spec's questions
- **herdr socket.** A user systemd unit reaches it. Tested with `systemd-run --user` and no herdr variables in its environment. No pane poller.
- **Naming herdr prompt senders.** The source checks' scan, last 24 hours at 3:06 PM ET, found a candidate sender for 283 of 428 plain user texts, 66 percent. That is a candidate hit rate from a cruder matcher, not verified accuracy. The rules above are stricter, so the named share will be lower. The real figure comes from the running index at a commit.
- **Codex messages.** No cross-session blocks. Codex sessions send herdr prompts (7 in that window) and receive them, and those are rows under the prompt rules.
- **Refresh cost.** Simple polls. The arithmetic adds the measured read times. State: 2 s poll + 3 ms + 5 s page fetch, about 7 s against a 15 s target. Screens: 4 s poll + 92 ms + 5 s fetch, about 9.1 s against 10 s, at 25 panes. This is unverified at 40 agents and on the running service.
